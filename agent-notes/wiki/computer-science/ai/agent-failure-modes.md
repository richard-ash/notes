# Agent Failure Modes

**Agent failure modes** are the recurring ways an autonomous AI agent degrades or breaks *in daily use* — as opposed to bugs you catch while building it. Pawel Jozefiak's June 2026 "field guide" (from months running a personal Claude Code + Codex agent that runs his day) organizes them into six patterns, each with a fix that holds up in production. His framing is deliberately general: the same failures hit ChatGPT, Claude, a Zapier flow, or an off-the-shelf framework, not just hand-rolled agents.

This is the failure-side complement to [[harness-engineering]] (which designs the environment so these don't happen) and [[agent-harness]] (which exposes products to agents). Jozefiak explicitly lands on **harness engineering** as the discipline underneath every fix: when an agent fails a challenge, the problem is almost never the model — it is the scaffolding (context, tools, memory, verification, permissions) that could not let it get there.

## The root cause: reliability is multiplicative, not additive

The reason agents break at all is arithmetic, not model stupidity. An agent works in **steps** — read, call a tool, decide, act, check, repeat — and step success rates *multiply*. At 99% per step, ten steps succeed ~90% of the time, a hundred steps ~37%, a thousand steps basically never. Jozefiak cites [research measuring this directly](https://arxiv.org/abs/2509.09677), and notes it is worse than the naive product because errors are **correlated**: one wrong step nudges the next one wrong.

The load-bearing consequence: every unit of *surface* you add — more tools, more memory, more steps, more things the agent can touch — multiplies risk rather than adding it linearly. This "step math" quietly explains all six failure modes below, and is the same insight behind [[agi-timelines|Karpathy's "march of nines"]] (each additional nine of reliability is a constant-difficulty grind) and the [[ai-coding-harnesses|harness]] emphasis on keeping the loop tight.

## The six failure modes

**1. Overbuilding.** You keep adding pieces because each is individually useful; the *pile* is the problem. More components mean a higher probability something is broken at any moment, and past a point the tools fight the agent. Microsoft names this **tool-space interference**: too many tools and the model picks the wrong one, burns tokens, or hallucinates a call. Cited studies put the tool-selection-accuracy drop at 7–85% as the catalog grows, worst for tools in the middle of a long list (the same *lost-in-the-middle* effect as long context). OpenAI caps a request at 128 tools; Cursor warns quality slips well before a few dozen — the cap is not where trouble starts. **Context rot** is the same shape: [Chroma's research](https://www.trychroma.com/research/context-rot) across 18 frontier models found accuracy falling 30–50% as the window filled, showing up around 300–400K tokens on million-token models — degradation from *noise*, not from running out of room. Fixes: prune skills/tools/memory periodically; keep the core config tight; and structurally, **search-then-load** — the agent keeps a small index and loads only the few tools it needs for the task, and treats the context window as a budget it compacts on purpose. (This is the negative case for [[agentic-engineering-architecture|"fat skills, fat code, thin harness"]] and progressive disclosure.)

**2. One agent doing everything.** The romantic "Jarvis" single mind is fine for tight personal context, but as work gets complex it becomes a monolithic codebase — heavier and harder to maintain until you spend more time managing the agent than getting value. Jozefiak stages the live field debate without resolving it: Anthropic's [multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system) (lead agent + clean-context subagents) beat a single agent by 90%+ on their evals but burned ~15× the tokens and was *worse* for tightly-coupled work like coding; Cognition's ["Don't Build Multi-Agents"](https://cognition.com/blog/dont-build-multi-agents) argues splitting context makes agents fragile because actions carry implicit decisions and conflicting decisions compound. His synthesis: **one agent stays in charge of the thread and does the writing/acting; extra agents fetch context and intelligence rather than take conflicting actions.** The seam to cut on is *context* — spin off a subagent or workflow the moment a task drags in a big, specific pile of context the main agent doesn't otherwise need (a whole codebase, a month of project history, a research dig), and have it hand back a result. The trick is instructing the main agent *when to delegate*, or it reverts to the monolith. (Cf. [[patron-not-wizard]], where models autonomously spawn their own sub-agent fleets.)

**3. Poisoning its own memory.** An agent with memory is great until it remembers something wrong — then one bad entry is recalled a hundred times, wrong forever on a loop. This only shows up in use. Microsoft's red-teaming names a cousin, **session context contamination**, where junk from one context leaks into the next and steers the agent off course. Fix: treat memory with the discipline of code — verify before saving, and use **layers** rather than one bucket. A small **working memory** for the task at hand; a **durable layer** for facts that outlive the session, where every durable fact carries a **source and a date** so it can be traced and retired when stale. The agent is allowed to *question its own memory* — a drift check that fires when a saved fact stops matching reality. "A fact with no source and no expiry is a rumor your agent will repeat with full confidence, forever." (This is a direct rationale for source-and-date memory hygiene — the same provenance discipline [[llm-knowledge-bases]] applies to compiled notes.)

**4. No fallback.** A 24/7 agent needs a fallback for the *model*: the fused base model will sooner or later be rate-limited, deprecated, or down. A fallback is not a permanent plan B — it is what keeps the lights on when the primary goes dark. Jozefiak runs an OpenRouter gateway for provider failover, but warns a *single* fallback is not a guarantee (OpenRouter itself went down ~50 minutes in August 2025, taking its own fallbacks with it), so he **layers** it: a gateway for provider failover plus a small local model (a 35B on a Mac Mini) as a floor for when the network itself is the problem. The most-skipped lesson: **a fallback you have never tested is not a fallback** — pull the primary on purpose on a quiet day and watch whether the agent fails over or falls on its face.

**5. Trusting it without checking.** The scariest failures are quiet: the agent says *done* and did nothing, writes a success log line, and you believe it. Tie this back to the step math — without checking each step you never see the 37%, only the green light. Fix: **check the outcome, not the activity.** A log line is not proof; whether a function ran without throwing tells you almost nothing. Did the file actually change, the message actually send, the row actually land in the database? *Re-run the exact thing that was failing and watch it pass.* Make the check safe to run twice (because you will), and keep an inspectable trail — Jozefiak is "religious about commits as save points" and runs a watchdog whose whole job is catching the silent skip before it compounds. "A fix is done when I re-run the exact thing that was failing and watch it pass. Until then it is a guess wearing a green checkmark." (This is the reliability-side mirror of [[ai-code-review|ensemble verification]] and [[harness-engineering]]'s snapshot-before / trigger / snapshot-after validation loop.)

**6. Never challenging it.** Aimed at custom-agent builders: throw scenarios the agent has rarely seen — rapid-fire messages, weird formats, requests with no obvious handler — *before* a real situation does. When a challenge fails, the problem is almost never the challenge; it is the architecture that could not let the agent get there. Keep a small set of nasty cases (the weird formats, the three-tools-in-a-row request) and re-run them every time you change the architecture — a **regression test for an agent**. When one fails, the harness is a short list to look at: how context gets in, how tools are exposed, how memory is stored and recalled, how work gets verified, what the agent is and isn't allowed to touch. "When it breaks, do not reach for the model. Look at what stopped it, and fix that." (This is the practitioner statement of [[ai-coding-harnesses]]'s benchmark point: same model, different harness, large swing.)

## The through-line: harness engineering

All six fixes converge on one claim — echoed by Microsoft's [year of red-teaming agents](https://www.microsoft.com/en-us/security/blog/2026/06/04/updating-taxonomy-failure-modes-agentic-ai-systems-year-red-teaming-taught-us/) from the security side — that **systems passing model-level tests still fall apart under real pressure, because the failure lives in the system, not the brain.** Jozefiak's stance is that overbuilding is worth doing for a while ("that is how you find the edges"), but the day you start *using* an agent is the day you start breaking it, and each break is a map to the next thing worth fixing. This is the same "the discipline lives in the scaffolding, not the code" thesis as [[harness-engineering]], reported from a solo operator's daily-driver agent rather than an OpenAI-internal codebase.
