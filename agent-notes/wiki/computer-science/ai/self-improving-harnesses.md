# Self-Improving Harnesses

**Self-improving harnesses** are agent systems where the harness itself — the code orchestrating prompts, tool calls, subagents, context management, memory, and workflow — becomes the object of optimization, edited by the very model it wraps. Lilian Weng's July 2026 survey "Harness Engineering for Self-Improvement" organizes the recent research literature (auto-research systems, self-evolving agents, evolutionary program search) around one question: how much of **recursive self-improvement (RSI)** runs through the harness layer rather than through a model rewriting its own weights?

The RSI lineage goes back to I. J. Good's (1965) "ultraintelligent machine" that designs better machines, and Yudkowsky's (2008) framing of an AI using its current intelligence to improve the cognitive machinery producing that intelligence. Weng's core move is to take "deployment system" seriously as part of that machinery: the layer between the raw model and the world "seems to be as important as the model's raw intelligence," and her predicted near-term RSI path starts not with weight-rewriting but with harness engineering evolving into *meta-methodology* — improving the machinery for getting better answers, not just the answers.

This is the research-literature counterpart to the practitioner cluster already in this wiki: [[ai-coding-harnesses]] (the anatomy of the tool loop), [[harness-engineering]] (Lopopolo's hand-crafted environment design at OpenAI), [[custom-harnesses]] (Vo's build-your-own playbook), and [[agent-harness]] (Taylor's business-facing version). Those describe humans designing harnesses; this literature asks what happens when the design loop closes and the agent does it.

## What a harness is, and its design patterns

Weng defines a harness as the system surrounding a base model that "orchestrates execution and decides how the model thinks and plans, calls tools and acts, perceives and manages context, stores artifacts, and evaluates results." Compared with the early "agent = LLM + memory + tools + planning" framing, harness engineering adds workflow design (loop engineering), evaluation, permission controls, and persistent state management — closer to runtime and OS design than to prompt templating. She draws the OS analogy explicitly: encapsulate complicated logic behind a simple interface, and expect configs, tool interfaces, and protocols to standardize across the industry.

Three recurring patterns:

1. **Workflow automation** — a goal-oriented plan → execute → observe/test → improve loop that runs *until* the goal is achieved, with the model analyzing its own trajectories and failures through an "agent runtime" rather than a static prompt.
2. **File system as persistent memory** — durable state lives in files, not context. Logs, diffs, traces, and past trajectories outgrow any context window, and since reading/writing files via `bash` is a foundational LLM skill, file-based memory automatically benefits from core-capability improvements. (The same design instinct as the repo-as-system-of-record principle in [[harness-engineering]].)
3. **Sub-agents and backend jobs** — parallelism made *explicit and inspectable*: subagent outputs stored as files, logs, and status records rather than transient chat context, so the parent agent can recover after interruptions and reason over its own execution history.

Her coding-agent case study notes the core interface has stabilized across Claude Code, Codex, OpenCode, and Cursor-style agents — file tools, shell, git, MCP/skills, web, artifacts, cron, and agent delegation around a single tool-call loop, the same loop [[ai-coding-harnesses]] dissects.

## The optimization ladder

The through-line of the survey is a progression in *what gets optimized*: instruction prompts → structured context → workflow → harness code → optimizer code. As models get stronger, the target gets more complex and the method more generic.

**Context engineering** is the first rung above prompts. ACE (Agentic Context Engineering; Zhang et al. 2025) treats context as an evolving playbook of itemized bullets maintained by a generator/reflector/curator trio — the key design being that the curator never rewrites a full prompt blob (which causes context collapse and brevity bias) but merges incremental, identified entries with deterministic logic. MCE (Meta Context Engineering; Ye et al. 2026) goes bi-level: it separates the *mechanism* of context management (a "skill" — static components plus dynamic operators) from the *content*, evolving skills at the meta level via agentic crossover over a skill-history database while the base level optimizes the skill-conditioned context from rollout feedback. Notably, both levels run in ordinary agentic coding environments with the standard Read/Write/Edit/Bash/Glob/Grep tool set, and a context function is literally a directory of files. Meta-Harness (Lee et al. 2026) goes a level deeper still — the optimized object is the *code* that decides what to store, retrieve, and present; it is "a harness for optimizing harnesses," producing a Pareto frontier of harness candidates, with the full execution history greppable on the file system rather than shoveled into one prompt. Weng's takeaway: **once harness design becomes an executable search space, a strong coding agent can exploit the same design space human engineers use.**

**Workflow design** can be handcrafted by experts — the AI Scientist pipeline (Lu et al. 2026, *Nature*: ideas → code → experiments → manuscript → peer review), ScientistOne (Meng et al. 2026, with verifiability as the central constraint: every citation, number, method, and conclusion must trace to an evidence source audited by Chain-of-Evidence checks), and Autodata (Kulikov et al. 2026, a challenger/weak-solver/strong-solver/verifier ensemble synthesizing training data at "just right" difficulty — though Weng notes that because the loop fine-tunes only the weak solver, it is closer to indirect distillation than RSI). Or it can be *searched*: ADAS (Hu et al. 2025) runs "meta-agent search" where a meta-agent programs new agentic workflows in code against an archive of prior designs, and AFlow (Zhang et al. 2025) represents workflows as graphs and optimizes them with MCTS, beating both manual designs and ADAS on QA/code/math.

## Whole-harness self-improvement

Context and workflow are each only one component; the fuller ambition is to optimize context logic, workflow, permissions, and everything else together. Weng's slogan: code is the universal language of systems, and an LLM that can optimize the code executing agents has access to a much larger design space than hand-written prompts.

- **STOP** (Self-Taught Optimizer; Zelikman et al. 2023) is the early landmark: improve not the solution but the *improver* — a program that recursively rewrites itself, judged by meta-utility over downstream tasks. It spontaneously discovered genetic algorithms, decompose-and-improve, prompt bandits, simulated annealing, and beam search. The **cautionary result**: STOP improved with GPT-4 but *degraded* with GPT-3.5 and Mixtral. Recursive structure alone is not enough — the base model must be capable enough to improve the mechanism, which is a [[the-bitter-lesson]]-flavored reminder that intelligence remains the core and the harness is leverage on it.
- **Lin et al. (2026)** sharpen that dependency by disentangling two axes: *harness-updating* (can the model produce useful harness edits?) turns out to be roughly **flat** across model scale — a 9B model writes skills "procedurally isomorphic" to Opus 4.6's — while *harness-benefit* (can the model exploit the improved harness?) is **non-monotonic**, with middle-tier models benefiting most. Benefiting requires timely, correct tool/skill invocation and long-horizon instruction following, which small models lack and top models need less.
- **Self-Harness** (Zhang et al. 2026) closes the loop with a propose–evaluate–accept cycle: *weakness mining* (cluster failures into verifier-grounded patterns, with rich causal records because identical surface errors — timeout, missing artifact — can have different root causes), *bounded proposal* (the model, given the editable surfaces, failure patterns, passing behaviors to preserve, and prior edit history, proposes narrow, diverse edits targeting recurrent addressable errors), and *validation* (accept only edits with no regression on both held-in and held-out splits). Run with MiniMax M2.5, Qwen3.5-35B, and GLM-5 on Terminal-Bench-2, it learned *model-specific* harness instructions targeting each base model's distinct weaknesses.
- **AHE** (Agentic Harness Engineering; Lin et al. 2026) diagnoses the bottleneck as **observability** — when a rollout fails, which of the harness's seven components (system prompt, tool description, tool implementation, middleware, skill, sub-agent config, long-term memory) is responsible? Its three pillars: component observability (every editable component is a file, every failure pattern maps to one component), experience observability (an "agent debugger" condenses raw trajectories into per-task root-cause reports aggregated into a benchmark overview — layered access is more token-efficient), and decision observability (an "evolve agent" makes every edit a file-level *falsifiable claim* with a predicted impact checked next round). Crucially, the runs directory, tracer, verifier, and LLM config are read-only, structurally disabling a class of reward hacks (disabling the verifier, swapping the model, raising the reasoning budget). On Terminal-Bench-2 AHE beat human-designed harnesses (OpenCode, Terminus-2, Codex) except on the Hard tier, and the frozen evolved harness transferred to SWE-bench Verified — evidence it encoded general engineering experience rather than benchmark-specific tricks.

The diagnostic machinery here — mapping failures to system components rather than blaming the model — is the automated version of the claim in [[agent-failure-modes]] that "the failure lives in the system, not the model," and AHE's agent-debugger/evolve-agent split echoes the independent-reviewer principle in [[ai-code-review]].

## Evolutionary search over harnesses

Evolutionary methods fit harness search well: the space is extensive and weirdly shaped, gradients are unavailable, but candidates are (sometimes) cheap to evaluate. The lineage runs from prompt evolution (Promptbreeder, whose mutation prompts themselves evolve; GEPA, which mutates via natural-language reflection over trial-and-error trajectories) to program evolution: **AlphaEvolve** (Novikov et al. 2025) keeps a pool of candidate programs and prompts frozen LLMs for improvement diffs, with evolvable regions explicitly fenced by `# EVOLVE-BLOCK` markers and a meta-prompt that co-evolves alongside the solutions; **ShinkaEvolve** adds sample-efficiency machinery (parent sampling balancing rank against offspring count, embedding-based novelty rejection, a meta-scratchpad of successful patterns); ThetaEvolve folds in RL and in-context learning, and DemoEvolve seeds the archive with human expert demonstrations. The **Darwin Gödel Machine** (Zhang et al. 2025) is the harness-specific endpoint: a coding agent allowed to modify *its own* harness repository, with parents sampled by performance and inverse child-count; under a fixed Claude 3.5 Sonnet, DGM-discovered agents went from 20% to 50% on SWE-bench Verified and 14.2% to 30.7% on Polyglot, matching or beating handcrafted harnesses. Hyperagents (2026) adds a meta-agent controlling how task agents get modified.

Weng's boundary condition: this family works where fitness is automatic and quantifiable (matmul, GPU kernels, contests, scheduling) and struggles where evaluation is slow, ambiguous, or heuristic — plus compute efficiency of evolution is a standing concern.

**Joint optimization with weights** is the frontier past pure harness evolution: SIA (Hebbar et al. 2026) has a feedback-agent choose per-iteration whether to update the harness or the model weights, but Weng flags the evidence as provisional (the task agent, gpt-oss-120b, is far weaker than the Claude Sonnet 4.6 meta/feedback agents, and baselines are too weak to cross-reference). Continual Harness (Karten et al. 2026) pairs harness updating with distilling a strong teacher's labels on low-reward trajectories in long-horizon gameplay.

## Why full autonomy still fails, and the seven bottlenecks

Trehan & Chopra (2026) ran LLMs from research idea to paper with minimal scaffolding; of four expert-selected ideas only one was fully executed, and six failure modes recurred: bias toward training-data defaults (stale libraries and assumptions), implementation drift under execution pressure (retreating to the common simpler solution when the proposed method gets hard), memory/context degradation without persistent artifacts, over-optimism ("p-hacking and eureka-ing" per Bubeck et al. — "numerical duct tape" declaring victory over noise), insufficient tacit domain intelligence, and weak scientific taste (executable experiments that answer the wrong question). This list reads as the negative image of the trainable research sub-skills in [[ml-research-craft]] — taste, staring at outputs, logging everything — and the persistent-artifact and over-optimism failures are exactly what the harness patterns above (files as memory, verifier-grounded evidence) exist to patch.

Weng's remaining bottlenecks toward full RSI:

1. **Weak and fuzzy evaluators** — self-improvement loops work where metrics are fast and objective; research taste, novelty, and long-term value resist measurement. (The same verifiability bottleneck [[agentic-engineering]] identifies for agentic coding.)
2. **Context and memory lifecycle** — with her notable prediction that context engineering "will and should become a core part of intelligence, rather than staying in the software system layer," by analogy to lifelong human memory.
3. **Negative results** — literature is biased toward successes, so models trained on it are bad at abandoning hypotheses or reporting failure; a research harness should make failed attempts easy to preserve.
4. **Diversity collapse** — evolutionary and RL loops exploit known high-reward patterns; open-ended research needs mechanisms to keep the population from collapsing into variants of one solution, especially when the best path initially scores worse.
5. **Reward hacking** — a loop optimizes whatever signal it gets (overfit unit tests, judge-specific tricks, benchmark artifacts); the evaluator and permission control should sit *outside* the evolving loop, with held-out tests, trace audits, and human review — AHE's read-only verifier is the concrete instance.
6. **Long-term success** — coding agents optimize short-term task completion, while repo health (maintainability, ownership boundaries, migration cost, backwards compatibility) is invisible to sandbox-based RLVR training. This is the training-loop version of the comprehension-debt worry in [[ai-code-review]].
7. **The role of humans** — "humans should move up the stack, not be removed from the loop": oversight at the right time and abstraction level, which is the RSI-scale version of the doing-to-commissioning shift in [[patron-not-wizard]].

## Synthesis: where this sits in the harness cluster

Two tensions worth holding. First, **the internalization question**: Weng predicts many harness improvements will eventually be absorbed into core model behavior — as prompt-engineering tricks were absorbed by instruction tuning — while the interface to external context and tools remains. That is a bitter-lesson-shaped prediction ([[the-bitter-lesson]]): hand-engineered scaffolding as a temporary crutch that general capability eats. But her own survey cuts both ways — STOP's model-dependence says the harness is only leverage on intelligence, while Lin et al.'s flat harness-updating curve says even small models can *write* the scaffolding; what scales is the ability to *use* it. If harness authorship is commoditized and harness benefit peaks mid-tier, the durable value sits in evaluators, permissions, and observability — precisely the components Weng insists must stay outside the loop.

Second, **the practitioner convergence**: the research systems surveyed here (file-based memory, greppable execution history, layered trace summaries, edits as falsifiable predictions) independently arrive at the same designs the practitioner accounts reached by hand — Lopopolo's agent legibility and repo-as-system-of-record in [[harness-engineering]], the thin-harness principle in [[agentic-engineering-architecture]], the self-improving "dreaming" skills Sierra reports in [[company-wide-agent]]. The literature is, in effect, automating the job those posts describe humans doing — which is also its warning: Weng's own concern about Self-Harness-style work is that a program editing its own OS breaks abstraction boundaries, so the editable surface, permission control, and security layers must be designed to live outside what the loop can touch.

The appendix catalogs the benchmark substrate this research selects on — PaperBench (replicate ICML papers against 8,316 author-co-developed rubrics), CORE-Bench (computational reproducibility), ScienceAgentBench, RE-Bench (agents beat human experts at 2-hour budgets but lose at 8+ hours), MLE-bench (Kaggle), and KernelBench (GPU kernels) — worth noting because bottleneck #1 (evaluators) and #5 (reward hacking) are both statements about exactly these verifiers.
